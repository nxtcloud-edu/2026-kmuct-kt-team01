# Git 및 협업 규칙

## 브랜치와 PR

- 제출 기준: `main`
- bootstrap: `bootstrap/20260920`
- 역할 작업: `work/20260920/role-N`
- 통합 후보: `assemble/20260920`
- 모든 역할 PR의 base는 `main`이며 작업 중 Draft PR을 일찍 공유한다.
- 기존 브랜치와 PR은 재사용한다. 강제 reset과 force push를 하지 않는다.
- 기능 구현과 검증이 끝난 실제 단위마다 의미 있는 커밋을 push한다. 빈 커밋과 횟수 채우기를 하지 않는다.

## 통합과 검토

역할 3만 통합 후보에 역할 커밋을 `1 → 3 → 4 → 5 → 2` 순서로 모은다. 교차 검토는 역할 1→3, 역할 2→5, 역할 3→1·4, 역할 5→2 순서이며 역할 1은 최종 통합 후보도 검토한다. 작성자가 자기 PR을 승인하지 않으며 최신 head SHA의 실제 diff를 기준으로 검토한다.

## 변경 요청

기본 채널은 요청 하나당 GitHub 이슈 하나다. 이슈를 만들 수 없으면 관련 PR 댓글을 사용한다.

- 제목: `ZZIK:20260920:role-<발신번호>:<고유ID>`
- 필수 본문: from, to, kind(`change|review|decision`), 관련 PR, head SHA, 필요한 결과, 수락 기준
- 상태: `REQUESTED → ACK → READY → APPLIED`
- READY: 실제 브랜치, full SHA, 변경 파일, 실행한 검사 기록
- APPLIED: 요청자가 결과를 직접 적용하고 검사한 뒤에만 전환

## 세션 인계

각 역할은 작업 단위 종료·중단 전에 `docs/assembly/role-N.md`에 현재 단계, 최근 커밋, 열린 PR, 검사, 남은 일, 차단 의존성, 요청 ID와 상태를 기록하고 push한다. 재개할 때 원격을 먼저 fetch하며 중복 구현과 중복 PR을 만들지 않는다.

## 안전 규칙

- 테스트는 전용 `_test`/`_e2e` DB와 임시 저장소만 사용한다.
- 운영·데모 데이터와 다른 참가자의 AWS 리소스를 수정하지 않는다.
- 비밀값을 저장소·이슈·PR에 남기지 않는다.
- mock/fixture와 실제 AWS 결과를 구분한다.
- 미구현·부분 구현·미검증·실패를 그대로 기록한다.
- 빨간 검사를 무시한 병합, 계정 위장, 형식적 승인, 가짜 성과 기록을 금지한다.
